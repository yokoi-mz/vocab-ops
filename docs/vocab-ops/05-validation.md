# 05 語彙更新検証

## 何をするか

足す語と外す語の両方を含む更新案について、反映してよいかを、過去の履歴を使って確かめる。改善したかどうかを見るのではなく、**更新案が増減モードの狙いに対して許せる結果か**を確かめる関門である。

## 入力と出力

- 入力：更新案、増減モード、過去の履歴
- 出力：合格／不合格、比較判定の内訳（改善・悪化・同等の件数）

## いつ行うか

| 更新案の中身 | 語彙更新検証 |
|---|---|
| 足すだけ | 行わない（そのまま反映） |
| 外すだけ | 行わない（そのまま反映） |
| 足す語と外す語の両方 | 行う。合格の基準は増減モードで決まる |

## 比べるもの

検証に使う履歴の原文それぞれについて、次の2つの文を比べる。

| 文 | 使ってよい語 |
|---|---|
| 手札語彙文 | 今の手札語彙とノーカン語彙だけ |
| 提案語彙文（`proposedSetSentence`） | 更新案を反映した手札語彙とノーカン語彙だけ |

- 保存済みの手札語彙文は、そのときの手札語彙・モデル・プロンプトの版・設定が今と同じなら、そのまま使う。同じでなければ、今の手札語彙で作り直す。
- 提案語彙文は、毎回新しく作る。
- 作り直した手札語彙文と提案語彙文は、文生成の履歴とは別に記録する（`01-history.md`）。

## 比較判定

複数件の「原文・手札語彙文・提案語彙文」をまとめて LLM に渡し、どちらが原文の意味をより忠実に表しているかを判定させる。

```
問題1
原文：メアリーにあの事を尋ねた。
文1：I say that to Mary.
文2：I ask Mary about that.
```

- 判定の基準は、**原文の意味がどれだけ正確に保たれているか**。文の自然さや長さは基準にしない。
- 判定は3択：手札語彙文のほうが忠実（悪化）／提案語彙文のほうが忠実（改善）／実質的な差がない（同等）。
- 判定は JSON などで出力させ、プログラムで機械的に集計する。
- 2つの文のどちらを先に見せるかが判定に影響しうるので、提示の順番は入れ替える。

例：40件の判定が「改善15・悪化3・同等22」なら、改善の可能性がある。ただし多数決だけでなく、悪化の件数と割合も見る。

## 決まったこと

- **語彙更新検証を行うのは、足す語と外す語の両方を含む更新案だけ。**
- **合格の基準は、増減モードごとに変える。**

  | 増減モード | 合格の基準 |
  |---|---|
  | 増やす | 悪化が多ければ見送る |
  | 変えない | 改善が悪化を上回れば採用 |
  | 減らす | 同等が多く、悪化が許容範囲なら採用（改善は必須ではない） |

- **具体的な数値は、LLM の判定のぶれを測ってから決める。** 同じ手札語彙で2回作った文どうしを比べさせ、本当は差がないのに「改善」「悪化」と判定される割合を先に測る。その割合を上回る差だけを、本物の差とみなす。
- 合格すれば、人間の承認なしで手札語彙に反映する。不合格なら反映を見送る。
- 改善がはっきりしないときは見送る、保守的な仕組みを基本とする。
- 1回の語彙更新の費用の上限には、検証のための文生成と比較判定も含める（`parameters.md`）。保存済みの手札語彙文をできるだけ使い回して、作り直しを減らす。

## 実装の段階で確かめること

- 同じ文の組を何回か判定させたときの、結果の一致率
- 判定のぶれ（同じ手札語彙で2回作った文どうしの比較）
- 複数件をまとめて判定させたときの、精度と費用
- 2つの文を見せる順番が判定に与える影響
- 自動で反映するときの、合格の基準の数値

結果は `experiments/` に記録する。

- **検証に使う履歴は、直近30件の文生成から無作為に20件と、それより前の文生成から無作為に10件を選ぶ（仮。件数は `parameters.md`）。** 直近の履歴は更新案の候補選びにも使われているので、それより前の履歴も混ぜる。それより前の文生成が10件に満たないときは、あるだけ使う。
- **合格の基準の数値は、仮の値で始める（`parameters.md`）。** 判定のぶれを測ったら決め直す。
- **比較判定は、10組ずつまとめて LLM に渡す。** 2つの文のどちらを先に見せるかは、1組ごとに交互に入れ替える。判定が読めなかった組は、件数に入れない。
- **手札語彙文や提案語彙文を作れなかった履歴は、その組を飛ばす。** 判定できた組が1つもなければ、不合格（見送り）とする。
- **費用の上限（`parameters.md`）に達したら、検証を途中でやめ、その語彙更新は失敗として記録する。** 手札語彙は変えない。
- **反映する直前に、手札語彙の版が語彙更新を始めたときと同じかを確かめる。** 違っていたら（途中でほかの語彙更新が反映されていたら）、反映せずに見送る（`01-architecture.md` の「手札語彙の一貫性」）。

## 未決

- **検証に使う履歴の選び方（仮の方法を見直すかどうか）。** いろいろな履歴を選ぶことが大切。最初の方針では「直近の一定件数」と「それ以前の全履歴から無作為に選んだ件数」を組み合わせる案だった。直近の履歴は更新案の候補選びにも使われているので、更新案に有利な判定になりやすい点に注意する。ほかに、更新案に関係する語が出てくる履歴と、関係しない履歴を組み合わせる案もある。選び方とその呼び方は、あとで検討する。
- 合格の基準の具体的な数値（今は仮の値）。
- **比較判定のプロンプトの書き直し。** 今のプロンプトは「意味の忠実さだけを比べる」としか書いていないため、「乗り降りする場所」のようにぼかした言い換えでも、意味は伝わっていると判定されることがある（2026-10-18 の試験で、`station` を使えるようになった提案語彙文が「同等」と判定された）。具体的な情報（場所、物、出来事など）を、ぼかさずに伝えているかを判断の基準として明記する。
- **提案語彙文の作り方の見直し。** 提案語彙文は手札語彙文と同じプロンプト（意味が伝われば不自然でもよい、細かいニュアンスは捨ててもよい）で作っているため、文が単純になりすぎることがある。手札語彙文の目標の文を、使える語の範囲で元の意味をできるだけ多く残すことを優先するように書き直す。
- 上の2つは、リポジトリの外で同じ組を何回か作らせ・判定させる実験で比べてから直す。そのあとで、判定のぶれを測り、合格の基準の数値を決め直す。
- 直近の履歴と過去の履歴を、別々に集計して基準を変えるか。
